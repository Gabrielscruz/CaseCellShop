## 2. Diagrama de Sequência: Vitrine de Produtos com Cache-Aside

```mermaid
sequenceDiagram
    autonumber
    actor Cliente as Cliente / Frontend
    participant API as ProductsController
    participant Cache as RedisCacheService
    participant Redis as Redis Server
    participant Repo as PrismaProductRepository
    participant DB as PostgreSQL 16

    Cliente->>API: GET /products?limit=10&cursor=...
    API->>Cache: getOrSetWithFallback(key, ttl=30s, fallback=24h, loader)
    Cache->>Redis: GET catalog:cursor:...:limit:10
    
    alt 1. Cache HIT (Quente)
        Redis-->>Cache: JSON Serializado dos Produtos
        Cache-->>API: { data, cacheStatus: "HIT" }
        API-->>Cliente: HTTP 200 (x-cache-status: HIT) [< 5ms]
    else 2. Cache MISS (Com Lock Anti-Stampede)
        Redis-->>Cache: null
        Cache->>Redis: SET lock:catalog:... "locked" PX 2000 NX
        
        alt 2.1. Lock Adquirido com Sucesso
            Cache->>Repo: loader() -> findPaginated({ limit, cursor })
            Repo->>DB: SELECT * FROM products ORDER BY created_at DESC, id DESC LIMIT 11
            DB-->>Repo: Registros do Catálogo
            Repo-->>Cache: Produtos e NextCursor
            Cache->>Redis: SETEX catalog:... 30s (Cache Primário)
            Cache->>Redis: SETEX fallback:catalog:... 86400s (Cache Fallback)
            Cache->>Redis: DEL lock:catalog:...
            Cache-->>API: { data, cacheStatus: "MISS" }
            API-->>Cliente: HTTP 200 (x-cache-status: MISS)
        else 2.2. Lock Ocupado (Outra thread já está calculando)
            Cache->>Cache: Delay curto de 80ms
            Cache->>Redis: GET catalog:cursor:...:limit:10
            Redis-->>Cache: Dados aquecidos pela thread anterior
            Cache-->>API: { data, cacheStatus: "HIT" }
            API-->>Cliente: HTTP 200 (x-cache-status: HIT)
        end
    else 3. Fallback Gracioso (Queda do Banco de Dados)
        Cache->>Repo: loader()
        Repo-->>Cache: Falha (PostgreSQL Connection Timeout)
        Cache->>Redis: GET fallback:catalog:...
        Redis-->>Cache: Cópia preservada de 24h
        Cache-->>API: { data, cacheStatus: "STALE" }
        API-->>Cliente: HTTP 200 (x-cache-status: STALE) [Vitrine não cai!]
    end
```

## 3. Diagrama de Sequência: Checkout Assíncrono com Idempotência e SAGA

```mermaid
sequenceDiagram
    autonumber
    actor Cliente as Cliente / Checkout
    participant API as OrdersController / Service
    participant Redis as Redis (Idempotência)
    participant DB as PostgreSQL (Transação Atômica)
    participant AMQP as RabbitMQ (Exchange)
    participant Worker as OrdersConsumer (Background)

    Cliente->>API: POST /checkout { customerId, items } [x-idempotency-key]
    API->>Redis: SET idempotency:key "PROCESSING" NX EX 120s
    
    alt Chave de Idempotência Já em Processamento
        Redis-->>API: Lock recusado (Key já existe com "PROCESSING")
        API-->>Cliente: HTTP 409 Conflict ("Transaction is already being processed")
    else Transação Concluída Anteriormente (Retry de Rede)
        Redis-->>API: Retorna JSON do Pedido Existente
        API-->>Cliente: HTTP 202 Accepted { orderId, status: "ACCEPTED" } (Sem novo débito!)
    else Novo Pedido (Lock Adquirido)
        API->>DB: BEGIN TRANSACTION
        loop Para cada item do carrinho
            API->>DB: UPDATE stock SET qty = qty - Q WHERE product_id = ID AND qty >= Q
            alt Saldo Insuficiente
                DB-->>API: 0 linhas afetadas
                API->>DB: ROLLBACK
                API->>Redis: DEL idempotency:key
                API-->>Cliente: HTTP 409 Conflict ("Insufficient stock for product X")
            end
        end
        API->>DB: INSERT INTO orders (total_amount, idempotency_key, status: ACCEPTED)
        API->>DB: INSERT INTO order_items (...)
        API->>DB: COMMIT TRANSACTION
        
        API->>AMQP: Publish 'order.created' { orderId, items, correlationId }
        API->>Redis: SET idempotency:key { orderId, status: ACCEPTED } EX 86400s
        API-->>Cliente: HTTP 202 Accepted { orderId, status: "ACCEPTED" }
        
        Note over Worker: Worker Assíncrono Desperta
        AMQP->>Worker: Entrega mensagem 'order.created'
        Worker->>Worker: Aguarda 30 segundos (Delay programado)
        Worker->>DB: UPDATE orders SET status = "PROCESSING"
        Worker->>Worker: Simula Chamada Gateway ERP (30s)
        
        alt Faturamento Aprovado no ERP
            Worker->>DB: UPDATE orders SET status = "BILLED"
            Worker->>AMQP: channel.ack(message)
        else Falha Irrecuperável no ERP
            Note over Worker: Transação Compensatória (SAGA)
            Worker->>DB: UPDATE stock SET qty = qty + Q (Estorna Estoque)
            Worker->>DB: UPDATE orders SET status = "FAILED", failure_reason = "..."
            Worker->>AMQP: channel.nack(message, requeue: false) -> Envia para DLQ
        end
    end
```

## 4. Diagrama de Transição de Estados do Pedido (State Machine)

```mermaid
stateDiagram-v2
    [*] --> ACCEPTED : POST /checkout\n(HTTP 202 com baixa atômica de estoque)
    
    ACCEPTED --> PROCESSING : OrdersConsumer consome mensagem\n(após delay de 30s)
    
    PROCESSING --> BILLED : Gateway ERP aprova faturamento\n(após processamento)
    
    PROCESSING --> FAILED : Timeout ou Recusa no ERP\n(Aciona Compensação SAGA e estorna estoque)
    
    BILLED --> [*] : Pedido Finalizado com Sucesso
    FAILED --> [*] : Mensagem encaminhada para DLQ ('orders.dlq')
```
