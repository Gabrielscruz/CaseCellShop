# ⚡ Infraestrutura de Cache com Redis

Este documento descreve a arquitetura de cache em memória utilizando **Redis 7**, abordando os padrões **Cache-Aside**, **Anti-Stampede Lock**, **Fallback Gracioso** e o controle de **Idempotência**.

---

## 1. Visão Geral: O que foi usado, Para que e Por que

| Aspecto | Especificação |
| :--- | :--- |
| **O que foi usado?** | **Redis 7 Alpine** com cliente nativo de alta vazão **`ioredis`**, executando com persistência AOF (*Append Only File*) e política de despejo de memória LRU configurada em [`infra/redis/redis.conf`](file:///home/gabriel/Documentos/CaseCellShop/infra/redis/redis.conf). |
| **Para que foi usado?** | 1. Armazenamento em memória do catálogo paginado.<br>2. Mutex atômico (*Distributed Lock*) para evitar Cache Stampede.<br>3. Réplica de Fallback Gracioso com TTL longo (24h).<br>4. Trava de concorrência e armazenamento de respostas idempotentes no checkout. |
| **Por que foi usado?** | Respostas com latência inferior a **2ms**, capacidade de absorver mais de 50.000 requisições/segundo em um único nó e alívio de mais de **90% das leituras** no banco de dados relacional. |

## 2. Padrões de Cache Implementados

### 2.1. Padrão Cache-Aside (Lazy Loading)
No [`ProductsService`](file:///home/gabriel/Documentos/CaseCellShop/app/src/modules/products/products.service.ts), a aplicação adota o padrão **Cache-Aside**:
* A aplicação verifica primeiro se os dados estão presentes no Redis sob a chave canônica:
  `catalog:cursor:{cursor}:limit:{limit}`
* **Se HIT:** Os dados serializados são desserializados e devolvidos ao cliente imediatamente.
* **Se MISS:** A aplicação busca os dados no PostgreSQL via repositório, armazena no Redis com TTL de **30 segundos** e retorna a resposta ao cliente.

### 2.2. Prevenção contra Cache Stampede (Dogpiling / Thundering Herd)
* **O Risco:** Quando o cache de uma vitrine com 10.000 produtos expira exatamente no momento em que 1.000 usuários acessam a página principal, todas as 1.000 requisições tentam consultar o banco ao mesmo tempo, causando saturação de CPU e colapso do PostgreSQL.
* **A Mitigação com Lock Distribuído:**
  No [`RedisCacheService`](file:///home/gabriel/Documentos/CaseCellShop/app/src/infra/cache/redis-cache.service.ts):
  ```typescript
  const acquiredLock = await this.acquireLock(key, lockTtlMs = 2000);
  if (!acquiredLock) {
    // Outra thread já adquiriu o lock para regenerar o cache.
    // Aguarda um intervalo curto de 80ms para que o cache seja populado:
    await delay(80);
    const retryCachedData = await this.get<T>(key);
    if (retryCachedData) return { data: retryCachedData, cacheStatus: 'HIT' };
  }
  ```
  O lock utiliza o comando atômico do Redis:
  ```text
  SET lock:catalog:cursor:... "locked" PX 2000 NX
  ```
  Isso garante que **apenas 1 thread** consulta o banco de dados; todas as demais threads aguardam e consomem o cache aquecido.

### 2.3. Fallback Gracioso (Stale Cache de 24 Horas)
* **Cenário de Desastre:** O banco de dados PostgreSQL sofre indisponibilidade temporária, saturação de conexões ou manutenção emergencial.
* **Mecanismo de Resiliência:**
  A cada recarga bem-sucedida do catálogo, o sistema salva duas chaves:
  1. `catalog:cursor:...`: Cache quente com TTL de **30 segundos**.
  2. `fallback:catalog:cursor:...`: Cache de segurança com TTL de **24 horas (86.400 segundos)**.
* **Comportamento em Falhas:**
  ```typescript
  try {
    const data = await loader(); // Tenta ler do PostgreSQL
    await this.set(key, data, ttlSeconds);
    await this.set(fallbackKey, data, fallbackTtlSeconds);
    return { data, cacheStatus: 'MISS' };
  } catch (error) {
    this.logger.warn(`Falha no banco. Acionando Fallback Gracioso...`);
    const staleData = await this.get<T>(fallbackKey);
    if (staleData) {
      return { data: staleData, cacheStatus: 'STALE' }; // A vitrine NÃO cai!
    }
    throw error;
  }
  ```
  O cliente recebe status HTTP 200 com cabeçalho `x-cache-status: STALE`, garantindo disponibilidade de 99.99% mesmo sob falha do banco primário.

## 3. Idempotência no Checkout com Redis

* **Lock de Transação em Andamento:**
  Ao receber um pedido com a chave `idempotencyKey`, o backend grava:
  ```text
  SET idempotency:{key} "PROCESSING" EX 120 NX
  ```
  - Se retornar `OK`: O lock foi adquirido com sucesso.
  - Se retornar `null`: Outra requisição com a mesma chave já está em processamento. O sistema rejeita chamadas concorrentes com `HTTP 409 Conflict`.
* **Armazenamento do Resultado:**
  Após a baixa atômica e criação do pedido no banco:
  ```text
  SET idempotency:{key} '{"orderId":"...","status":"ACCEPTED"}' EX 86400
  ```
  Qualquer nova tentativa dentro de 24 horas receberá a mesma resposta sem acionar novamente o banco ou o estoque.

## 4. Configuração Otimizada de Produção (`infra/redis/redis.conf`)

* **Política de Memória:** `maxmemory-policy allkeys-lru` (descarta as chaves menos utilizadas caso a memória atinja o limite máximo estipulado, garantindo que o Redis nunca trave).
* **Persistência Híbrida:** RDB + AOF com `appendfsync everysec` para garantir tolerância a desastres e reinicializações de contêineres sem perda do histórico de idempotência.
