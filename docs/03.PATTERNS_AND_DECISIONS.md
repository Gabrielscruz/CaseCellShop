# 🧠 Padrões Arquiteturais e Decisões Técnicas

Este documento detalha as decisões de engenharia adotadas no **CaseCellShop**, com foco em consistência em alta concorrência, resiliência assíncrona e estratégias de paginação de dados.

---

## 1. Padrão SAGA e Transações Compensatórias

### 1.1. O Problema da Transação Distribuída
No fluxo de checkout sob alto volume, realizar a reserva de estoque, gravação do pedido e faturamento síncrono no ERP na mesma requisição HTTP causa:
* **Gargalo de Latência:** O ERP central é lento e responde em centenas de milissegundos ou segundos.
* **Travamento de Conexões:** Pool de conexões do banco de dados e do servidor HTTP saturam rapidamente.
* **Risco de Inconsistência:** Se o gateway do ERP falhar no final da requisição após a dedução do estoque, o cliente perde o saldo sem receber o pedido.

### 1.2. A Solução: Padrão SAGA Coreografado
O sistema implementa o **Padrão SAGA Assíncrono com Ação Compensatória**:

```text
[Cliente] ──POST /checkout──► [API Backend]
                                    │
                       (1. Baixa Atômica Estoque)
                                    ▼
                             [PostgreSQL]
                                    │
                      (2. Enfileira 'order.created')
                                    ▼
                               [RabbitMQ]
                                    │
                                    ▼
                         [Worker: OrdersConsumer]
                                    │
                         (3. Chama Gateway ERP)
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
               [Sucesso]                        [Falha]
             Status: BILLED               1. SAGA COMPENSATÓRIA:
                                             incrementStockAtomic()
                                          2. Status: FAILED
                                          3. Encaminha para 'orders.dlq'
```

### 1.3. Código da Transação Compensatória
No [`OrdersConsumer`](file:///home/gabriel/Documentos/CaseCellShop/app/src/infra/messaging/orders.consumer.ts):
```typescript
try {
  await this.simulateErpBilling(orderId);
  await this.orderRepo.updateStatus(orderId, OrderStatus.BILLED);
} catch (error) {
  // Transação Compensatória (Saga): Restitui imediatamente o estoque reservado
  for (const item of items) {
    await this.productRepo.incrementStockAtomic(item.productId, item.quantity);
  }
  await this.orderRepo.updateStatus(orderId, OrderStatus.FAILED, error.message);
  this.metrics.queueMessagesDlqTotal.inc();
  throw error; // Encaminha mensagem para a Dead Letter Queue (DLQ)
}
```

## 2. Idempotência no Checkout (Anti-Duplicidade e Retries)

### 2.1. O Desafio do Duplo Clique e Retries de Rede
Usuários em conexões instáveis de celular frequentemente sofrem com timeouts locais e disparam múltiplos cliques no botão de "Finalizar Compra", ou sistemas de frontend reenviam requisições de checkout.

### 2.2. A Solução com Redis e Fingerprint SHA-256
A idempotência atua em duas camadas:
1. **Identificação da Requisição:** O cliente pode enviar o cabeçalho `x-idempotency-key`. Caso não envie, o backend gera um fingerprint criptográfico determinístico:
   $$\text{Fingerprint} = \text{SHA256}(\text{customerId} + \text{JSON.stringify}(\text{sortedItems}))$$
2. **Lock de Processamento (`SET NX EX 120s`):**
   - Ao receber a requisição, o [`RedisCacheService`](file:///home/gabriel/Documentos/CaseCellShop/app/src/infra/cache/redis-cache.service.ts) tenta gravar a chave `idempotency:{key}` com valor `"PROCESSING"`.
   - Se o lock já existir com valor `"PROCESSING"`, o backend rejeita com [`TransactionInProgressError`](file:///home/gabriel/Documentos/CaseCellShop/app/src/core/errors/conflict.error.ts) (`HTTP 409 Conflict`).
   - Se a transação já foi concluída, o Redis retorna o resultado idêntico em cache, devolvendo o `orderId` existente em **menos de 5ms**, sem debitar o estoque pela segunda vez.
3. **Persistência do Resultado:** O resultado da compra é salvo no Redis com TTL de **24 horas** (`86400s`).

## 3. Paginação Baseada em Cursor (Cursor-Based Pagination)

### 3.1. Por que NÃO usar Paginação por Offset (`LIMIT / OFFSET`)?
Em uma vitrine com 10.000 ou 1.000.000 de capinhas de celular, `OFFSET n` apresenta dois defeitos graves:
1. **Custo Computacional $O(N)$:** Para buscar `OFFSET 8000 LIMIT 20`, o banco de dados precisa ler e ordenar os primeiros 8.020 registros no disco para descartar os primeiros 8.000.
2. **Anomalia de Linhas Repetidas / Perdidas (Data Drift):** Se novos produtos forem adicionados no topo enquanto um usuário navega da página 1 para a 2, itens se deslocam e o usuário visualiza o mesmo produto duas vezes ou perde produtos.

### 3.2. A Abordagem por Cursor Opaque
No [`cursor.util.ts`](file:///home/gabriel/Documentos/CaseCellShop/app/src/utils/cursor.util.ts):
* O cursor é codificado em **Base64URL** a partir da tupla do último item:
  ```json
  {
    "createdAt": "2026-09-22T21:41:00.000Z",
    "id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11"
  }
  ```
* A consulta no PostgreSQL usa a tupla de ordenação:
  ```sql
  SELECT * FROM products
  WHERE (created_at < $cursorCreatedAt)
     OR (created_at = $cursorCreatedAt AND id < $cursorId)
  ORDER BY created_at DESC, id DESC
  LIMIT 1001;
  ```
* **Performance:** Com o índice composto B-tree `idx_products_created_at_id`, a busca pula diretamente para a posição física no índice em **tempo $O(1)$ constante**, independente da profundidade da página.

## 4. Baixa Atômica Condicional e Blindagem contra Overselling

### 4.1. Por que checagem simples de estoque (`SELECT` seguido de `UPDATE`) falha?
```text
Thread A: SELECT qty FROM stock (vê qty = 1) ──────────┐
Thread B: SELECT qty FROM stock (vê qty = 1) ──┐        │ (Ambas decidem vender!)
Thread A: UPDATE stock SET qty = 0 ────────────┼────────┘
Thread B: UPDATE stock SET qty = 0 ────────────┘ (Overselling! 2 vendas para 1 unidade)
```

### 4.2. A Solução: Atomic Conditional Update no Banco
No [`prisma-product.repository.ts`](file:///home/gabriel/Documentos/CaseCellShop/app/src/infra/database/prisma-product.repository.ts), a baixa é realizada de forma condicional e atômica:
```typescript
await tx.stock.update({
  where: { productId },
  data: {
    qty: { decrement: quantity },
  },
});
```
Aliado à constraint física declarada no PostgreSQL:
```sql
ALTER TABLE stock ADD CONSTRAINT chk_stock_qty CHECK (qty >= 0);
```
O PostgreSQL utiliza lock a nível de linha (*Row-level Exclusive Lock*) apenas durante a instrução `UPDATE`, garantindo que:
* Múltiplas requisições simultâneas para o mesmo produto são serializadas no nível do registro.
* Se o saldo for menor que a quantidade comprada, a operação é rejeitada instantaneamente sem comprometer outros produtos.

## 5. Delay Programado de 30s no Consumer (Simulação de Esteira Realista)

### 5.1. Motivação e Racional
* No cenário real de um e-commerce integrado a um ERP legado, a resposta de checkout é assíncrona porque etapas complexas ocorrem em segundo plano:
  1. Análise de risco e motor antifraude (ClearSale, Konduto, etc.).
  2. Autorização de crédito e reserva na adquirente de cartão.
  3. Geração de nota fiscal e remessa contábil no ERP monolítico.
* Se o worker respondesse em 1 milissegundo no teste, o pedido passaria para `BILLED` antes que o avaliador ou o frontend pudesse consultar o status `ACCEPTED` ou `PROCESSING`.
* **Configuração:** O [`OrdersConsumer`](file:///home/gabriel/Documentos/CaseCellShop/app/src/infra/messaging/orders.consumer.ts) aplica um delay controlado de **30 segundos** entre as etapas de transição:
  $$\text{ACCEPTED} \xrightarrow{30s} \text{PROCESSING} \xrightarrow{30s} \text{BILLED}$$
* Isso demonstra a integridade da esteira assíncrona, a capacidade de consulta via polling (`GET /orders/:id/status`) e a robustez contra timeouts HTTP.

## 6. Desacoplamento de Erros (Domain Errors ➔ Interceptor ➔ Filter)

### 6.1. O Problema de Usar `HttpException` no Service
Quando um `Service` lança `new NotFoundException()` ou `new ConflictException()`, a regra de negócio passa a depender diretamente do protocolo de transporte HTTP. Caso o mesmo serviço seja consumido por uma fila RabbitMQ, gRPC ou WebSocket, o transporte HTTP vazaria para esses canais.

### 6.2. A Arquitetura Implementada
```text
[Service de Negócio] ──throw InsufficientStockError──┐
                                                    ▼
                                       [ErrorHandlerInterceptor]
                                                    │
                                (Converte para ConflictException 409)
                                                    ▼
                                         [GlobalExceptionFilter]
                                                    │
                               (Emite Log Estruturado + JSON Uniforme)
                                                    ▼
                                           [Resposta HTTP 409]
```
* **Linguagem Ubíqua em Inglês:** Todas as mensagens de erro e exceções seguem o idioma padrão da indústria (`Insufficient stock for product "X". Transaction cancelled.`).
